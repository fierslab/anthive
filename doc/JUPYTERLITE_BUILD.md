# JupyterLite: build, client and tests

Anthive serves a JupyterLite site at `/jupyter/`. It is a static build with a
Pyodide kernel, so every notebook runs in the user's browser and calls the
REST API under the same origin (`{origin}/api/`), with the user's login
cookie. Nothing runs on the server for it.

## Sources and build

- `frontend/jupyter/jupyter/` is the contents folder: the shipped notebooks
  (`Getting_Started.ipynb`) and the vendored client `vark/`.
- `make build-jupyter` runs `jupyter-lite build` with pinned versions and
  writes the site to `webapp/jupyter/` (or `JUPYTER_OUT=<dir>`). The dev Caddy
  serves `webapp/`. The images build the same thing in `docker/Dockerfile`
  (stage `jupyter`); the pins in both places must agree, and
  `tests/test_jupyterlite_static.py` checks that they do. The Makefile comment
  above the target explains why `jupyterlite-core` and `notebook` are pinned
  together.
- Pyodide itself (0.29.3 with the current kernel) and its packages come from
  `cdn.jsdelivr.net` when a kernel starts.
- `jupyter-lite.json` at the repo root is not picked up by the current build:
  the built site still says `appName: JupyterLite`. Treat it as dead until
  someone wires it in.

The Caddy routes that matter (`config/Caddyfile`): `/jupyter` redirects to
`/jupyter/`, `/jupyter/*` is served from the build with
`Cross-Origin-Opener-Policy: same-origin` and
`Cross-Origin-Embedder-Policy: require-corp` (Pyodide needs a cross-origin
isolated page), and `/api/*` goes to ant-serve with the prefix stripped. On
an Authelia site `/jupyter/` needs the login cookie.

The web UI opens notebooks generated by ant-serve with
`/jupyter/lab/index.html?fromURL=/api/notebook/{b64}/{name}.ipynb` (dataset
page and plot page buttons). JupyterLite saves them in the browser's own
storage, at the top level, next to the bundled `vark/`.

## The vendored client

`frontend/jupyter/jupyter/vark/` is an unchanged copy of `vark/*.py` from
pyvark ([codeberg.org/mfiers/pyvark](https://codeberg.org/mfiers/pyvark)).
The kernel's working directory is the contents root, so `import vark` finds
it without an install. vark talks HTTP through `requests`, which Pyodide does
not preinstall: a notebook must `await micropip.install(['requests', ...])`
before `import vark` (`requests` comes from the Pyodide distribution and uses
urllib3's browser fetch backend).

To update it, commit in the pyvark checkout, then

```sh
make vendor-pyvark PYVARK=../pyvark
```

This copies the files and writes `frontend/jupyter/vendored_pyvark.json`
(version, pyvark commit, sha256 of every file). Do not edit the vendored
files by hand: `make test` compares them with the record.

## Tests

Three levels, from fast to slow.

`make test` runs `tests/test_jupyterlite_static.py` with the rest of the
suite. No browser and no network. It checks the vendored files against the
record, the record against `__version__`, the client against the server's
`API_COMPATIBLE_PYVARK` and `API_VERSION`, the notebooks with nbformat (cell
ids, the `python` kernel name, code that compiles, `requests` installed
before `import vark`), the build pins, and a local build if there is one.
When a pyvark checkout sits next to this repo (or `PYVARK_DIR` names one)
and its version differs from the vendored one, you get a warning, or a
failure when `PYVARK_DIR` is set.

`make test-jupyter` is the browser end to end check
(`tests/test_jupyterlite_e2e.py`). It builds JupyterLite into a temporary
folder, serves it together with a proxy to ant-serve on one origin
(`tests/jupyterlite_proxy.py`, the same routes as Caddy) and drives
headless Chromium with playwright. It needs a running ant-serve
(`JUPYTER_API`, default `http://localhost:8080`), network access to the
Pyodide CDN and a Chromium for playwright
(`uv run --with playwright playwright install chromium`); without them the
tests skip and say why. It takes about two minutes.

`make test-live-site URL=https://host:port` checks a deployed site
(`tests/live/test_site_jupyterlite.py`). Give it an account through
`ANTHIVE_LIVE_USER` and `ANTHIVE_LIVE_PASSWORD`, or a `~/.netrc` entry for
the host. The login mode (Authelia form, basic auth or none) is detected
from how the site answers an anonymous request, or forced with
`ANTHIVE_LIVE_LOGIN`. The HTTP part signs in and compares the served
JupyterLite files with the checkout: the vendored vark by hash and the
notebooks byte for byte, so a site built from other sources fails. It also
checks the API version and `compatible_pyvark`, and that anonymous callers
see no internal dataset. The browser part signs in through the real login
page and repeats the kernel checks of `make test-jupyter` on the site:
vark version, `/health`, `/version`, the dataset list (an empty catalogue
passes), an expression query and a plot when a dataset exists, the shipped
notebooks, the kernel seeing the same datasets as the signed-in user, and
the 503 `warming_up` retry. A real `warming_up` answer only exists for a
few seconds after a restart, so the test fakes it by intercepting one
request in the browser. Certificates are not checked unless
`ANTHIVE_LIVE_VERIFY_TLS=1` (scratch sites use `tls internal`).
The release check runs it against the scratch site (`doc/RELEASING.md`).

The driver both browser suites share is `tests/jupyterlite_driver.py`. It
switches on JupyterLite's `exposeAppInBrowser` option by rewriting
`jupyter-lite.json` in flight (the served site is not changed) and runs code
through the JupyterLab application object.
